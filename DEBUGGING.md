# Инструкция по отладке потока данных (Troubleshooting)

Если контейнеры успешно запустились, но данные не появляются в S3 (MinIO), проблема может быть на одном из трех этапов потока: **MQTT -> Python Bridge -> Kafka -> Spark -> S3**.

Ниже описаны шаги, как отследить, где именно теряются данные. Все команды выполняются в терминале вашего сервера, где запущен `docker compose`.

---

## Шаг 1. Проверяем мост (Python Bridge)
Самая частая причина — мост не может подключиться к вашему внешнему MQTT брокеру из-за сетевых доступов, паролей или неправильного названия топика.

Посмотрим логи моста:
```bash
docker compose logs --tail=50 -f mqtt-to-kafka
```

**Что вы должны увидеть:**
- Строку `Connected to MQTT broker at 192.168.99.99:1803`
- Строку `Subscribed to topic: ha_to_node-red`
- Если данные идут, то в логах не должно быть ошибок `Error processing message`.
*(Если мост выдает `Connection Refused` или `Not Authorized`, перепроверьте данные в файле `.env` и убедитесь, что сервер с Docker имеет доступ к IP `192.168.99.99`).*

---

## Шаг 2. Проверяем брокер Kafka
Даже если мост читает MQTT, доходят ли сообщения до топика `raw_telemetry` в Kafka? Мы можем "подслушать" топик напрямую внутри контейнера Kafka.

Выполните команду для чтения сообщений из Kafka в реальном времени:
```bash
docker exec -it $(docker compose ps -q kafka) kafka-console-consumer \
  --bootstrap-server localhost:9092 \
  --topic raw_telemetry \
  --from-beginning \
  --max-messages 10
```

**Что вы должны увидеть:**
- Вывод JSON-строк, которые мост перекладывает из MQTT.
- Если команда просто висит и ничего не выводит (а в MQTT точно идут данные), значит проблема между мостом и Kafka.

---

## Шаг 3. Проверяем потоковую задачу Spark Streaming
Если данные в Kafka есть, но в MinIO (S3) они не появляются, нужно проверить Spark, который занимается их перекладкой. За это отвечает контейнер `spark-streaming-submit`.

Посмотрим логи сабмиттера:
```bash
docker compose logs --tail=100 -f spark-streaming-submit
```

**На что обратить внимание:**
- **Ошибки подключения к S3:** Если вы видите ошибки `Access Denied` или `Connection Refused` к S3, возможно, контейнер MinIO стартовал медленнее, чем Spark. Spark Streaming пишет данные каждые 60 секунд (настроено в коде `.trigger(processingTime="1 minute")`).
- **Отсутствие пакетов (No batches):** Spark может писать пустые батчи, если не видит новых сообщений в Kafka.

Вы также можете зайти в **Веб-интерфейс Spark Master** в браузере:
👉 `http://<ip_вашей_vm>:8080`
- Убедитесь, что там есть живой `Worker` (в разделе Workers).
- Убедитесь, что приложение `KafkaToS3Streaming` находится в статусе `RUNNING`.

---

## Шаг 4. Проверяем бакет в MinIO
Возможно, данные туда пишутся, но структура папок скрыта или интерфейс не обновился.

Так как контейнер `minio-init` завершает работу после инициализации бакета, вы можете использовать `docker compose run` для выполнения одноразовой команды:
```bash
docker compose run --rm minio-init mc ls myminio/datalake/
```

Если вы видите файлы формата `.parquet`, значит поток работает корректно, и данные успешно приземлились в S3!
